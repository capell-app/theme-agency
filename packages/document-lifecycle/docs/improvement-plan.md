# Document Lifecycle — Improvement & Growth Plan

> Package: capell-app/document-lifecycle · Kind: package · Tier: premium · Product group: Capell Operations · Bundle: operations · Status: Draft

## 1. Snapshot

Document Lifecycle is an admin/database package that turns "controlled documents" (terms, privacy, policy, operational docs) into evidence-grade records: a registry (`Document`), immutable versioned publications with SHA-256 content hashes (`DocumentPublication`), and acceptance records that extend the existing `legal_acceptances` table (`DocumentAcceptance`). Behaviour lives entirely in Actions (`RegisterDocumentAction`, `PublishDocumentAction`, `PublishDocumentFromPublishingRevisionAction`, `ResolveLatestDocumentPublicationAction`, `ComputeDocumentContentHashAction`, `RecordDocumentAcceptanceAction`, plus status/health helpers); the admin surface (`DocumentResource` + two read-only relation managers) can register documents, publish manual versions, archive/restore records, and record authenticated-admin acceptances. A `PublishingRevision::created` listener auto-publishes when a registered document's underlying model is published in Publishing Studio. Requires `capell-app/core`, `capell-app/admin`, `capell-app/publishing-studio`; supports `capell-app/customer-portal` via a portal self-service feed (`DocumentLifecyclePortalSelfServiceItemProvider`). Current marketplace summary, verbatim: _"Controlled document registry, publication metadata, hashes, and acceptance evidence for Capell CMS."_ Screenshots: **1** declared in `capell.json` (`docs/assets/marketplace/extension-card.jpg`), but `docs/screenshots.json` defines **4** required admin captures — a mismatch (manifest under-declares marketplace media).

## 2. Improvements (existing functionality)

- **Make `HasFactory` real or remove it.** — All three models `use HasFactory` and `composer.json` maps `Capell\DocumentLifecycle\Database\Factories\` → `database/factories`, but that directory and the factory classes do not exist. `Document::factory()` will throw at runtime; every test works around this with `Model::query()->create([...])`. Ship `DocumentFactory`, `DocumentPublicationFactory`, `DocumentAcceptanceFactory` (with states `draft`/`active`/`archived`, `fromRevision`, etc.) so consumers and screenshot/demo seeders can use them. — `composer.json`, `src/Models/Document.php`, `src/Models/DocumentPublication.php`, `src/Models/DocumentAcceptance.php` — **S**
- **Promote the health check from a version-only stub to a real diagnostic.** — `DocumentLifecycleHealthCheck` only implements `compatibleCapellApiVersion()`. The premium sibling `packages/payments/src/Health/PaymentsHealthCheck.php` adds `report(): PaymentsHealthReportData` backed by an Action. Mirror that: a `BuildDocumentLifecycleHealthReportAction` that asserts the 3 required tables exist, the `legal_acceptances` extension columns are present, the morph map + protected tables are registered, and the publishing-revision listener is wired. — `src/Health/DocumentLifecycleHealthCheck.php` — **M**
- **Add document status colours + label trait.** The status badge column renders with no colour (`->badge()` only) and `DocumentStatusEnum` is a plain backed enum with hand-rolled `statusOptions()` in the resource. Adopt the project `HasLabels` trait + `HasColor`/Filament `HasLabel`, and drive the Select/badge from the enum. — `src/Enums/DocumentStatusEnum.php`, `src/Filament/Resources/Documents/DocumentResource.php:71`, `:141` — **S**
- **Decouple acceptance evidence from the live `request()`.** `RecordDocumentAcceptanceAction::handle()` reads `request()->ip()` / `request()->userAgent()` internally. In the queue/console paths (and `console` is a declared surface) `request()` is empty, so `ip_hash`/`user_agent_hash` silently become null and the evidence is incomplete with no signal. Accept optional `?string $ipAddress`, `?string $userAgent` params (defaulting to `request()` at the call site) so the Action is context-pure. — `src/Actions/RecordDocumentAcceptanceAction.php:49-50` — **S**
- **Give `legal_acceptances` a `down()` that only reverses what its `up()` added.** The rollback unconditionally drops `legal_acceptances_acceptor_subject_lookup` + `legal_acceptances_doc_publication_lookup` and the two columns, even when `up()` took the "table already existed" branch and added only `document_publication_id` + `document_hash` (not the acceptor/subject index). On such installs `down()` will attempt to drop an index the package never created. Guard each `dropIndex` with `Schema::hasIndex(...)` (already used in `up()`) and track ownership. — `database/migrations/2026_05_10_190868_03_extend_legal_acceptances_for_document_lifecycle.php:67-85` — **S**
- **Tighten `DocumentAcceptance` mass-assignment.** It uses `$guarded = []` while the sibling models declare explicit `$fillable`. Even though writes go through Actions, an open guard on an evidence/audit table is a smell; declare `$fillable` for consistency and defence-in-depth. — `src/Models/DocumentAcceptance.php:44` — **S**
- **Index `Document.documentable` for reverse lookups used by the listener.** `PublishDocumentFromPublishingRevisionAction::documentForRevision()` queries `whereIn('documentable_type', ...)->whereIn('documentable_id', ...)`. The migration indexes `documentable` via `nullableMorphs(...idx)` (good), but the hot path also `->first()` with no ordering — fine, yet confirm the composite type+id morph index is actually hit (it is, via the generated index). No change needed if verified; otherwise add `index(['documentable_type','documentable_id'])`. — `database/migrations/2026_05_10_190868_01_create_document_lifecycle_documents_table.php:22` — **S**
- **Document the auto-publish coupling.** The `PublishingRevision::created` global listener fires `PublishDocumentFromPublishingRevisionAction` on _every_ revision row app-wide and early-returns when no registered `Document` matches. That's correct but invisible; one extra query per revision create. Note it in `docs/overview.md` and consider a config flag to disable, for hosts that don't use auto-publish. — `src/Providers/DocumentLifecycleServiceProvider.php:146-153` — **S**

## 3. Missing Features (gaps)

Mapped to `capabilities[]`: `document-lifecycle`, `document-lifecycle-admin`, `document-lifecycle-acceptance`, `document-lifecycle-customer-portal-document-feed`.

- **Admin lifecycle actions (closed for the feasible Now slice).** The admin now uses Action-backed create, publish-version, archive, restore, and record-authenticated-admin-acceptance flows, all gated through the existing `DocumentPolicy` update/create checks and backed by package Actions rather than inline lifecycle writes. Void acceptance, bulk acceptance operations, and richer acceptor targeting remain part of the export/re-acceptance work below rather than this completed row. — ties to `document-lifecycle-admin`.
- **Retention / expiry policy.** No expiry, review-due date, or supersession metadata on `Document`/`DocumentPublication`. Document-management norms expect "valid until / review by" and automatic status transition (Active → Archived) on expiry. Differentiator: scheduled command that flips expired documents and surfaces "review due" in admin + portal feed.
- **Acceptance reminders / re-acceptance enforcement.** When a new version publishes, prior acceptors are silently stale. No mechanism to flag who must re-accept, or to notify them. This is the natural premium hook off `document-lifecycle-acceptance` (reminder schedule, "outstanding acceptances" report).
- **Bulk operations.** No bulk publish, bulk archive, or bulk export of acceptance evidence (CSV/PDF). Compliance buyers expect an exportable acceptance ledger per document/version. Table-stakes for the target buyer.
- **e-Signature / signed evidence artifact.** Acceptances store hashes but no signed/exportable certificate (e.g. a signed JSON or PDF proof bundling document hash + acceptor + timestamp). Strong differentiator vs ad-hoc logging.
- **Public frontend output for consent.** `surfaces` advertises `frontend` yet there is no public route/Blade (overview.md says so explicitly; `frontendRenderBudgetMs: 0`). A safe, render-data-only consent component ("Accept current Terms" widget that calls `RecordDocumentAcceptanceAction`) would make the `frontend` surface real and is the obvious cross-sell with consent flows. Must follow Capell public-output safety (no model IDs, hashes, or admin internals leaked).
- **Diagnostics health report (see §2).** `document-lifecycle-admin` implies discoverability; the stubbed health check leaves the manifest's `critical` claim unbacked.
- **Per-version diff / content snapshot.** Publications store a hash and metadata but not the published content snapshot, so admins can't see _what_ changed between versions. Storing (or referencing) the `after_payload` snapshot enables a version diff view.

## 4. Issues / Risks

- **Manifest "frontend" surface is not real public output.** `surfaces: ["admin","console","frontend"]` and capability `document-lifecycle-customer-portal-document-feed`, but `providers.frontend: []` and no routes/views exist. The only "frontend" is the customer-portal self-service feed, which is auth-gated portal data, not anonymous output. Risk: marketplace/diagnostics consumers expecting a public surface. Either drop `frontend` from `surfaces` until a public component ships, or ship the consent component in §3. — `capell.json` (surfaces), `docs/overview.md` ("does not register public frontend routes"), `src/Support/CustomerPortal/DocumentLifecyclePortalSelfServiceItemProvider.php`
- **`critical` health check asserts nothing.** Manifest label: _"…surfaces, providers, and install health are discoverable by Diagnostics."_ Implementation validates only the API version string. No package-owned health test exists (`grep` of `tests/` for `HealthCheck` → none). For a `severity: critical` entry this is a manifest-vs-implementation mismatch. — `src/Health/DocumentLifecycleHealthCheck.php`, `capell.json` (healthChecks)
- **`HasFactory` is a broken promise / dead autoload.** `composer.json` autoloads a non-existent `database/factories` and models expose `factory()` that cannot resolve. Latent runtime error for any consumer/test that calls it. — `composer.json`, `src/Models/*`
- **Acceptance hashes can silently be null off the HTTP path** (queue/console), weakening the evidence the package is sold on. — `src/Actions/RecordDocumentAcceptanceAction.php:49-50`
- **Asymmetric migration rollback** can throw on the "table pre-existed" install path (drops an index it didn't create). — `migrations/...03_extend_legal_acceptances...php:67-85`
- **PHP constraint drift.** `composer.json` requires `php: ^8.3` while the Capell baseline is PHP 8.4. Harmless (broader floor) but inconsistent with siblings; confirm intentional. — `composer.json`
- **Sensitive output flag set but unbacked by enforcement.** `performance.cacheSafety.sensitiveOutput: true` and `cacheable: false` are correct intent (hashes, IP/UA hashes, acceptor identities are PII-adjacent). The portal feed `meta` exposes `acceptance_id`, `document_publication_id`, `document_key`, `document_version` to the portal account — acceptable for the owner's own records, but there is no test proving a portal account cannot see _another_ account's acceptances beyond the `acceptor_id`/`subject_id` scoping. Add a negative test (account B must not see account A's items). — `src/Support/CustomerPortal/DocumentLifecyclePortalSelfServiceItemProvider.php:19-57`, `tests/Feature/CustomerPortalDocumentFeedTest.php`
- **`adminQueryBudget: 40` is undefended.** No test asserts the index/edit/relation-manager pages stay within budget; the index uses `withCount('publications')` + `latest('updated_at')` (fine), but there's no regression guard. — `capell.json` (performance), `src/Filament/Resources/Documents/DocumentResource.php:61`
- **i18n gap.** `resources/lang/en/navigation.php` exists; no other locales. Portal feed and admin strings are translation-keyed (good), so this is purely a coverage gap, not a leak.
- **Test gaps (covered vs not):** Covered — publish/hash/immutability (`DocumentPublicationTest`), revision listener + documentable repointing, acceptance recording + config fallback (`RecordDocumentAcceptanceTest`), portal feed happy path + manifest (`CustomerPortalDocumentFeedTest`), admin visibility/forbidden/permitted (`DocumentLifecycleAdminTest`), schema + legacy-table adoption + protected-table/morph registration (`DocumentLifecycleSchemaTest`), nav + manifest contribution. **Not covered** — health check behaviour (none); factory usage (none, because broken); migration `down()`/rollback; portal-feed cross-account isolation; `RecordDocumentAcceptanceAction` off the HTTP path (null-hash behaviour); enum labels/colours; admin query budget.

## 5. Marketplace & Selling

**Critique.** The manifest `summary` and composer `description` are identical-ish and feature-list-flat ("registry, publication metadata, hashes, and acceptance evidence"). They state _what is stored_, not _what the buyer gets_ (defensible compliance evidence). Neither mentions the actual differentiator: tamper-evident, version-pinned proof of _which_ document version a user accepted, wired automatically to Publishing Studio. Composer `description` is also truncated vs the manifest (drops "for Capell CMS").

**Improved 1-sentence summary:**

> Tamper-evident proof of which document version was published and who accepted it — controlled documents, immutable hashed versions, and a court-ready acceptance ledger for Capell.

**Improved 3–4 sentence description:**

> Document Lifecycle turns terms, privacy, and policy documents into auditable records: every publication is version-pinned and content-hashed, and every acceptance captures the exact version, hash, actor, and timestamp. It hooks into Publishing Studio so a published revision automatically becomes an immutable document publication — no custom audit layer required. Acceptance evidence surfaces in the admin and (with Customer Portal) in each account's self-service history, and the tables are registered as protected so the audit trail can't be casually deleted. Built for compliance-sensitive Capell sites that must answer "which version did this user agree to, and when?"

**Screenshot/media gaps.** Manifest declares **1** marketplace image; `docs/screenshots.json` specifies **4** required admin captures (index, edit, publications RM, acceptances RM) that are not yet referenced in `marketplace.screenshots[]`. Action: capture the 4 and list them in the manifest. No demo/seed data path exists to populate them (blocked on factories — §2). No video/GIF of the auto-publish-on-revision flow, which is the most compelling demo.

**Pricing / tier / bundle positioning.** `premium` in the `operations` bundle, `Capell Operations` group — appropriate; compliance/governance is a willingness-to-pay feature. Strengthen by cross-selling on dependencies: hard-requires `publishing-studio` (anchor the "auto-publish" story to it), `supports` `customer-portal` (the acceptance-history feed is a portal upsell). Natural Extension-Suite framing: an "Operations / Compliance" suite = Document Lifecycle + Publishing Studio + Diagnostics + Password Policy (already the README "Best Used With" set). The retention/reminder/e-signature features in §3 justify the premium tier and a possible add-on tier.

**Differentiators / value props / target buyer.** Differentiator: content-hash immutability + automatic version pinning from Publishing Studio + protected audit tables — most CMS "terms acceptance" is an unversioned boolean. Target buyer: ops/compliance/legal owners of regulated or contract-heavy Capell sites (memberships, healthcare, finance, B2B SaaS portals) who need defensible "who accepted what version when" evidence.

**Keywords/tags (8–12):** `document-lifecycle`, `compliance`, `audit-trail`, `terms-of-service`, `consent-management`, `content-hash`, `versioning`, `legal`, `governance`, `acceptance-evidence`, `customer-portal`, `publishing`.
