# Login Audit — Improvement & Growth Plan

> Package: capell-app/login-audit · Kind: package · Tier: premium · Product group: Capell Operations · Bundle: operations · Status: Draft

## 1. Snapshot

Login Audit is an admin-only operations package (`surfaces: ["admin"]`) that wraps `rappasoft/laravel-authentication-log` + `tapp/filament-authentication-log` to record login / failed-login / logout events for Capell users and surface them in Filament. It owns the `login_audit` table (`database/migrations/2026_05_10_190857_01_create_login_audit_table.php`), a `LoginAudit` model extending the vendor `AuthenticationLog`, a settings group (`login_audit`), and admin surfaces: `LoginAuditResource`, `LoginAuditsWidget`, `LoginAuditsRelationManager`, plus a user-edit sidebar summary via `LoginAuditUserSchemaExtender`. Domain logic lives in four small Actions (`ResolveLoginAuditIpAddressAction`, `ShouldTrackUserIpAddressesAction`, `BuildLoginAuditsQueryAction`, `ApplyLoginAuditSettingsAction`); event capture itself is delegated entirely to the vendor listeners configured in `config/login-audit.php`. Two middlewares (`AdminActivityMiddleware`, `UserActivityMiddleware`) update `last_seen_at` on the most recent matching row. Deps: `capell-app/admin`, the two auth-log vendor packages. Current marketplace summary, verbatim: _"Login Audit records login, failed login, logout, and admin/user activity metadata for Capell users."_ — identical to the composer/manifest `description` and the manifest `marketplace.summary`. **Screenshot mismatch:** `capell.json` declares only **1** marketplace screenshot (`docs/assets/marketplace/extension-card.jpg`), yet `docs/screenshots/` ships **8** PNGs (4 surfaces × light/dark) and `docs/screenshots.json` describes 6 surfaces — the manifest under-represents available media.

## 2. Improvements (existing functionality)

Prioritized.

1. **Implement the stub health check** — `LoginAuditHealthCheck` only returns `compatibleCapellApiVersion()`; it performs no actual health assertion, but the manifest advertises it as `severity: critical` "surfaces, providers, and install health are discoverable by Diagnostics." — verify the `login_audit` table exists, the vendor listeners are wired, the `frontend.activity` alias is registered, and (optionally) that recent rows are being written. Currently Diagnostics reports nothing meaningful. — `src/Health/LoginAuditHealthCheck.php` — **S**

2. **Populate `last_activity_at` (or drop it)** — the column is created and asserted in tests, but no code writes it; both middlewares write `last_seen_at` only. The vendor base exposes `updateLastActivity()`. Either call it from the middleware or remove the column to avoid a permanently-null field that implies a feature. — `src/Http/Middleware/AdminActivityMiddleware.php`, `src/Http/Middleware/UserActivityMiddleware.php`, migration — **S**

3. **De-duplicate the two middleware bodies** — `AdminActivityMiddleware::updateUserActivity` and `UserActivityMiddleware::updateUserActivity` are ~90% identical (resolve IP, match on ip/user_agent, set `last_seen_at`, save). Extract a shared `UpdateLastSeenForActorAction` so both delegate to one Action (matches the skill's "UI delegates to Actions" convention; middleware currently holds query logic directly). — `src/Http/Middleware/*`, new `src/Actions/UpdateLastSeenForActorAction.php` — **M**

4. **`UserActivityMiddleware` matches the wrong row** — it takes the _first_ `authentications()` row matching ip+user_agent with no ordering, whereas `AdminActivityMiddleware` correctly uses `->where('login_at','<',$now)->latest('id')`. The user path can stamp `last_seen_at` on an arbitrary historical session. Align ordering with the admin path. — `src/Http/Middleware/UserActivityMiddleware.php:44-51` — **S**

5. **Fix the duplicate/typo vendor config key** — `AdminServiceProvider::register()` sets both `filament-authentication-log.resources.AuthenticationLogResource` and the misspelled `...AutenticationLogResource`. If this is a defensive shim for a vendor typo, add a one-line comment; otherwise remove it so the intent is clear. — `src/Providers/AdminServiceProvider.php:33-40` — **S**

6. **Avoid `now()->subHours()` drift in the widget query** — `BuildLoginAuditsQueryAction` filters `login_at >= now()->subHours(24)` with `latest('login_at')->limit(20)`. On a quiet site the widget shows nothing rather than the last N logins. Consider "last 20 logins" without the hard time floor, or make the window a parameter sourced from settings. — `src/Actions/BuildLoginAuditsQueryAction.php:27-31` — **S**

7. **Make the persistent admin middleware respect a setting** — `AdminActivityMiddleware` runs on every authenticated admin request and issues a SELECT + conditional UPDATE per request. `track_user_ip_addresses` is honoured for IP, but there is no switch to disable the per-request `last_seen_at` write entirely. Add a "track admin activity / online-now" toggle to `LoginAuditSettings` and short-circuit when off. — `src/Http/Middleware/AdminActivityMiddleware.php`, `src/Settings/LoginAuditSettings.php` — **S**

8. **Surface the `is_trusted` column in the UI** — the migration stores `is_trusted` and the vendor model has `markAsTrusted()/markAsUntrusted()`, but no table/relation-manager column or filter exposes trust state. The relation manager already shows `device_name`; add trusted/device columns so the stored data is reachable by operators. — `src/Filament/Resources/LoginAudits/Tables/LoginAuditsTable.php`, `src/Filament/Resources/Users/RelationManagers/LoginAuditsRelationManager.php` — **S**

## 3. Missing Features (gaps)

Manifest `capabilities`: `["login-audit", "login-audit-admin"]` — both are presence/visibility capabilities; there is no capability for detection, alerting, or export. Against security-audit norms:

- **Suspicious-activity detection (DIFFERENTIATOR, and the biggest gap).** The migration ships `is_suspicious` + `suspicious_reason`, the vendor base ships `markAsSuspicious()` and a `suspicious()` scope, and both the table and the user-bridge summary already _display/derive_ this data — yet **nothing in the package ever sets `is_suspicious`** (grep: zero writers in `src/`). The columns are permanently `false`. A `DetectSuspiciousLoginAction` (e.g. failed-attempt thresholds, new-country, new-device, multiple IPs in a short window) that flags rows on the vendor `Login`/`Failed` events would turn dead schema into the package's headline feature. — ties to a new `login-audit-detection` capability.
- **Impossible-travel / geo-anomaly (DIFFERENTIATOR).** `location` is a JSON column but is only ever filled by the optional `torann/geoip` path in vendor config (`notifications.*.location` defaults to `false`), so geo is effectively off out of the box. No haversine/elapsed-time check exists. Pair geo resolution on login with a travel-velocity check.
- **Alerting (TABLE-STAKES, currently passive).** `config/login-audit.php` exposes `notifications.new-device` (enabled) and `notifications.failed-login` (disabled) — both vendor notifications, none wired to Capell's own admin notification surface, and neither configurable from `LoginAuditSettingsSchema`. There is no admin-facing "alert me on N failed logins" or brute-force alert. Promote these into the settings schema and route through Capell admin notifications.
- **CSV / data export (TABLE-STAKES).** No export action on `LoginAuditResource` or the relation manager. Security teams expect to export an access log for an incident review.
- **Active-session / device tracking surfacing (TABLE-STAKES).** `device_id`, `device_name`, `is_trusted`, `last_activity_at` are stored (or meant to be) but only `device_id` is _read_ (user-bridge "recent_devices" count) — none are written by Capell code, and `active_sessions` in the bridge is derived purely from `logout_at IS NULL`, which never clears for sessions that simply expire. A real session/device panel (with logout-other-devices) is missing.
- **Retention rotation depth (TABLE-STAKES, partially present).** `ApplyLoginAuditSettingsAction` clamps `retention_days` into `login-audit.purge` and the monthly `login-audit:purge` command runs — but the schedule is **monthly**, so a "90 day" retention can hold rows up to ~120 days, weakening any GDPR/PII claim. Daily purge + a visible "last purged" indicator would close this.
- **Per-event-type coverage gaps.** Config wires `Login`, `Failed`, `Logout`, `OtherDeviceLogout` (all vendor). There is no handling of password-reset, lockout, or 2FA-challenge events, and no admin-impersonation audit trail — natural adjacencies for an "operations" security package.

## 4. Issues / Risks

- **PII / IP retention & GDPR.** `login_audit` stores IP, full user-agent, and (optionally) geo `location` indefinitely unless purge runs. Purge is **monthly only** (`AdminServiceProvider::registerSchedule()` → `->monthly()`), so the effective retention overshoots the configured `retention_days`. `track_user_ip_addresses=false` nulls IP on save via `LoginAuditObserver::saving()` and in `ResolveLoginAuditIpAddressAction`, which is good — but there is no equivalent control for user-agent or geo, and no anonymisation/truncation option (e.g. /24 masking). For a GDPR posture, document the lawful basis and add daily purge + UA/geo controls. — `src/Observers/LoginAuditObserver.php`, `AdminServiceProvider.php:80-92`
- **Write-volume vs performance budget.** Manifest sets `adminQueryBudget: 40` and `cacheSafety.cacheable: false`. `AdminActivityMiddleware` is registered **persistent on every admin panel request** and runs `SELECT ... latest('id')->first()` + conditional `UPDATE` each time. On a busy admin this is an extra read+write per request with no batching, debounce, or "only update if older than X minutes" guard — a realistic path to blowing the 40-query budget on dashboard pages that already run many widget queries. Add a throttle (only stamp if `last_seen_at` older than e.g. 60s). — `src/Http/Middleware/AdminActivityMiddleware.php`
- **Event-listener coverage is entirely vendor-owned and untested here.** The package itself registers no listeners; capture depends on `rappasoft` listeners being bound from `config/login-audit.php`. There is **no test asserting that a real `Login`/`Failed` event produces a `login_audit` row** — tests use `LoginAudit::factory()` to fabricate rows. If the host app overrides `auth.events` or the vendor wiring breaks (e.g. the Laravel 13 fork drift noted in the README), capture silently stops and nothing fails. Add an integration test that dispatches `Illuminate\Auth\Events\Login` and asserts a row.
- **Dead/unpopulated schema (tech debt + misleading UI).** `is_suspicious`, `suspicious_reason`, `is_trusted`, `last_activity_at`, `device_id`, `device_name` are created and (some) displayed, but never written by Capell code. `LoginAuditMigrationsTest` asserts the _columns exist_ — giving false confidence that the features behind them exist. Either implement the writers (Section 3) or trim the schema + UI columns. — migration, `LoginAuditsTable.php:71`, `LoginAuditsRelationManager.php:66`
- **Public-output safety: low risk, one thing to watch.** Package is admin-only (`surfaces: ["admin"]`, `frontendRenderBudgetMs: 0`), so the strict anonymous-leak rules mostly don't apply. However `UserActivityMiddleware` is aliased as `frontend.activity` and writes audit rows for _authenticated frontend users_; confirm it is never applied to anonymous routes (guarded by `$request->user() !== null`, which is correct) and that it never emits output. The widget builds raw `HtmlString` for the "last active" tooltip (`LoginAuditsWidget.php:116-122`) — interpolated values are framework-formatted dates/translations, not user input, so currently safe, but any future field injected there must be escaped. Authenticatable name rendering is already covered by the "renders authenticatable names as safe text instead of raw html" test.
- **Authorization surface.** `LoginAuditPolicy` only implements `viewAny`/`view` (read-only), and the relation manager hard-disables create/edit/delete — appropriate for an immutable audit log. `SiteScope::isGlobalActor()` short-circuits to allow; confirm that is the intended bypass for global admins. No `delete`/`forceDelete` policy means rows are only removable via the purge command, which is good for audit integrity but means an operator cannot redact a single erroneous PII row from the UI — a deliberate trade-off worth documenting.
- **i18n.** Most strings are translated (`capell-login-audit::*`, `capell-admin::*`). One leak: `LoginAuditDashboardSettingsContributor::settingsKeys()` returns hard-coded English `'label' => 'Access Logs'` and `'group' => 'System health'` instead of translation keys. — `src/Filament/Settings/Contributors/LoginAuditDashboardSettingsContributor.php:16`
- **Test gaps (enumerated).** Covered: migration columns/custom-table, settings schema + retention clamp, table/relation/widget metadata, IP resolver (CDN header valid/invalid/direct), IP-null-when-tracking-off, observer IP stripping, both middleware happy/guard paths, bridge enable/disable matrix, policy permission gate, orphaned-row placeholder, name-as-safe-text, provider registration. **Not covered:** any real auth-event → row capture; the health check (it's a stub); purge command actually deleting old rows; suspicious/trusted/geo behaviour (because none exists); the `last_activity_at` write (absent); the `now()->subHours(24)` empty-window behaviour of the widget query.

## 5. Marketplace & Selling

**Critique.** The current `marketplace.summary` and composer `description` are byte-identical ("records login, failed login, logout, and admin/user activity metadata for Capell users") and read like a changelog line, not a sell. "metadata" is vague; there is no benefit, no buyer, no differentiator, and it undersells the (latent) device/suspicious/geo schema. The composer `description` field is even weaker — "Authentication log for Capell" — and doesn't match the manifest summary. The manifest lists **1** screenshot while **8** are committed: the card has no in-product proof.

**Improved 1-sentence summary:**

> Tamper-proof access logging for Capell — track every login, failed attempt, logout, device, and session, with retention controls and an admin audit trail built for security and compliance reviews.

**Improved 3–4 sentence description:**

> Login Audit gives Capell operators a complete, immutable record of who accessed the admin and storefront, when, from which IP and device, and whether each attempt succeeded. A dedicated Filament resource, dashboard widget, and per-user access summary make it easy to spot unusual activity and respond to incidents, while configurable retention keeps the log lean and aligned with your data-protection policy. IP capture can be disabled or resolved through your CDN (Cloudflare and similar), and the audit log is read-only by design so records can't be quietly altered. Built on the battle-tested Laravel authentication-log foundation and wired into Capell's settings, permissions, and Diagnostics.

(Note: the device/suspicious/geo language is justified only once Section 3 features ship; until then, sell what's real — logging, retention, CDN-aware IP, read-only audit, per-user summary.)

**Screenshot/media gaps.** Promote the 8 existing PNGs into `marketplace.screenshots` (currently 1). `docs/screenshots.json` also names two surfaces whose images aren't committed yet — `user-edit-access-summary.png` and `user-login-audits-relation-manager.png` (README keeps them as text placeholders). Capture those and add a short "spotting a suspicious login" GIF once detection lands.

**Pricing / tier / bundle positioning.** Tier `premium`, bundle `operations`, group `Capell Operations`, `proposedLicense: paid`, `requestedCertification: first-party`, `supportPolicy: priority`. As shipped (a polished wrapper over a free OSS log) "premium/paid" is a stretch — the paid justification is the _operations/security_ layer, which today is thin (no detection, no export, no alerting). Either (a) build Section 3's detection + export + alerting to earn the premium tier, or (b) consider a standard tier until those land. Bundle fit is correct.

**Cross-sell.** Declared deps: `capell-app/admin` (hard requires). The manifest `dependencies.supports`/`conflicts` are empty — populate `supports` to enable bundling. Natural Extension-Suite cross-sells:

- **password-policy** — pair "enforce strong credentials" with "audit who logged in"; obvious security bundle.
- **privacy-center** — Login Audit holds IP/UA/geo PII; privacy-center can expose subject-access/erasure over the audit log (retention + anonymisation hooks).
- **diagnostics** — already the consumer of the (stub) health check; a working check makes Login Audit a first-class Diagnostics citizen.
- **access-gate** — gated areas + access logging is a coherent "who got in where" story.

**Differentiators / value props / target buyer.** Buyer: security-conscious site operators, agencies managing client Capell installs, and teams with compliance obligations (GDPR/SOC-ish). Value props: immutable read-only audit trail; CDN-aware accurate IP capture; configurable PII retention; per-user access summary inside the user editor; zero frontend cost (admin-only). The would-be differentiator vs every generic "auth log" plugin is the _unbuilt_ suspicious/impossible-travel detection — that is the wedge to a defensible premium product.

**Keywords / tags (8–12):** login audit, authentication log, security audit, access log, failed login tracking, GDPR retention, suspicious login detection, device tracking, session monitoring, admin activity, IP logging, compliance.
