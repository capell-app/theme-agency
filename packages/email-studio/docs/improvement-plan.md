# Email Studio — Improvement & Growth Plan

> Package: capell-app/email-studio · Kind: package · Tier: premium · Product group: Capell Communications · Bundle: communications · Status: Draft

## 1. Snapshot

Email Studio is the transactional-email backbone for Capell: it registers reusable templates (with locale/site variants), resolves a delivery profile, renders declared `{{ variable }}` placeholders into a stored snapshot, applies suppression checks, and dispatches a queued `SendEmailJob` that calls a provider adapter to deliver per-recipient and record outcomes. Provider event webhooks now write delivery audit events back into `email_events`; admin template authoring, one-click unsubscribe, tracking endpoints, and inbound reply ingestion remain open roadmap slices.

- **Surfaces (declared):** `admin`, `frontend`, `console` — in code: `routes/web.php` exposes tokenized provider-event ingestion, `FrontendServiceProvider::boot()` is still a no-op, and `AdminServiceProvider` owns MailTracker admin viewing/settings. The main product surface remains **console/queue + service container** plus the sent-email admin resource.
- **Key Actions:** `SendEmailAction`, `DeliverEmailMessageAction`, `RenderEmailTemplateAction`, `ResolveEmailTemplateVariantAction`, `RegisterEmailTemplateAction`, `CheckEmailSuppressionAction`, `SuppressEmailAddressAction` (`src/Actions/`).
- **Models/tables (10 + 1 FK migration):** `email_profiles`, `email_templates`, `email_template_variants`, `email_messages`, `email_recipients`, `email_events`, `email_replies`, `email_suppressions`, `email_template_registrations`, `email_tracking_tokens` (`database/migrations/2026_05_10_190847_*`, plus `2026_05_21_000001_add_site_foreign_keys_to_email_studio_tables`).
- **Support/infra:** `EmailVariableRenderer`, `EmailProfileResolver`, `EmailProviderRegistry`, `EmailTemplateRegistry`, `EmailAddressNormalizer`; provider adapters `SmtpEmailProviderAdapter`, `PostmarkEmailProviderAdapter` (extends SMTP), `FakeEmailProviderAdapter`; contract `EmailProviderAdapter`.
- **Dependencies:** requires `capell-app/admin`, `capell-app/core`, `capell-app/frontend`; supports `capell-app/campaign-studio`, `capell-app/form-builder`, `capell-app/insights`; conflicts none.
- **Declared capabilities:** `delivery-audit`, `provider-event-ingestion`, `provider-normalization-foundation`, `provider-adapters`, `suppressions`, `template-rendering`, `transactional-email`. Reply ingestion, unsubscribe, and first-party tracking remain unimplemented and are not listed as shipped capabilities.
- **Marketplace summary (verbatim):** "Email Studio is Capell's transactional-email engine: site-scoped reusable templates with safe {{ variable }} rendering, pluggable delivery profiles and provider adapters, suppression enforcement, and a queued, auditable per-recipient send pipeline."
- **Screenshots:** **1** declared in `capell.json` (`docs/assets/marketplace/extension-card.jpg`), but `docs/screenshots.json` has **0** entries and explicitly blocks capture ("No screenshot target exists … routes/web.php is intentionally empty").

## 2. Improvements (existing functionality)

- **Wire `EmailStudioHealthCheck` to actually run the 4 declared checks** — `capell.json` declares 4 health checks (template-rendering, provider-delivery, suppressions, provider-events) pointing at `EmailStudioHealthCheck`, but the class only implements `compatibleCapellApiVersion()` and asserts nothing. Health surface is currently a lie. — `src/Health/EmailStudioHealthCheck.php` — **M**
- **Done/Shipped: Persist real Symfony transport message IDs for SMTP/Postmark-over-Symfony sends.** `SmtpEmailProviderAdapter::send()` now reads the returned Laravel/Symfony `SentMessage::getMessageId()` and maps that provider transport ID onto every delivered recipient instead of fabricating `smtp-{message}-{recipient}` IDs. `PostmarkEmailProviderAdapter` inherits the same behavior through its Symfony mailer path. The fake adapter remains deterministic for local/test delivery only. — `src/Support/Providers/SmtpEmailProviderAdapter.php`, `tests/Fixtures/CapturingEmailStudioMailer.php`, `tests/Unit/EmailStudioDataAndSupportCoverageTest.php` — **M**
- **`SendEmailJob` has no retry/backoff/timeout policy** — no `$tries`, `$backoff`, `$retryUntil`, `$timeout`, or `failed()` handler. A transient SMTP failure marks the whole message `Failed` permanently (`DeliverEmailMessageAction::markProviderFailure`). Add tiered retries and a `failed()` hook that records the terminal failure. — `src/Jobs/SendEmailJob.php`, `src/Actions/DeliverEmailMessageAction.php` — **M**
- **Distinguish transient vs permanent provider failures** — `DeliverEmailMessageAction` catches `Throwable` and immediately sets every queued recipient + the message to `Failed`. There is no concept of a retryable error, so SMTP timeouts are treated like hard bounces. Introduce a retryable-exception path that rethrows for the queue to retry. — `src/Actions/DeliverEmailMessageAction.php` — **M**
- **Shipped 2026-06-05: Batch recipient status writes in the delivery loop.** `markNewSuppressions` now batches newly suppressed recipients, provider failures update by failure-reason bucket, successful recipient provider IDs write through a single upsert, and message status is derived from known delivery counts instead of re-plucking every recipient status. Manifest `adminQueryBudget` remains 40; keep broader send-size coverage on the Next pass. — `src/Actions/DeliverEmailMessageAction.php` — **Done**
- **`CheckEmailSuppressionAction` instantiated with `new`, bypassing the container** — `DeliverEmailMessageAction::markNewSuppressions` calls `(new CheckEmailSuppressionAction)->handle(...)` while the rest of the codebase uses `resolve()`/`::run()`. Inconsistent and unfakeable in tests. — `src/Actions/DeliverEmailMessageAction.php` — **S**
- **Body retention is configured but never enforced** — `body_retention_days` (default 90) exists in config and is documented, but no command/job prunes `rendered_html`/`rendered_text`. PII (full rendered emails) accumulates forever. Add a scheduled `PruneEmailBodiesAction` + console command. — `config/capell-email-studio.php`, `src/Models/EmailMessage.php` — **M**
- **`track_opens` / `track_clicks` config keys are dead** — documented in `docs/templates-and-providers.md` and present in config, but neither adapter injects a tracking pixel or rewrites links, and there are no tracking routes. Either implement or remove from config + docs to stop over-promising. — `config/capell-email-studio.php`, `src/Support/Providers/SmtpEmailProviderAdapter.php` — **L**
- **`PostmarkEmailProviderAdapter` is SMTP-in-disguise** — it only overrides `mailerName()` to `'postmark'`; it does not use the Postmark API, capture Postmark message IDs, or verify Postmark webhook signatures. Buyers reading "provider adapters" will expect a real Postmark integration. Either build it on the Postmark HTTP API or rename it to clarify it is "Postmark-over-Symfony-mailer". — `src/Support/Providers/PostmarkEmailProviderAdapter.php` — **M**
- **`EmailProfileResolver` default-provider ordering is partly inert** — it orders by `provider = default_provider` but still requires `is_default = true`; if multiple defaults exist across scopes the secondary ordering rarely matters, and there's no guard against >1 `is_default` per scope. Add a partial unique index or resolver tie-break test. — `src/Support/EmailProfileResolver.php` — **S**
- **Locale fallback is opaque** — `ResolveEmailTemplateVariantAction` resolves "requested or current locale before fallbacks" but the fallback chain isn't documented or configurable (no default-locale config key). Document and make the fallback locale a config value. — `src/Actions/ResolveEmailTemplateVariantAction.php` — **S**

## 3. Missing Features (gaps)

- **Done/Shipped: provider webhook + event ingestion.** `POST /mail/provider-events/{token}` resolves `EmailProfile.webhook_endpoint_token_hash`, validates `X-Capell-Email-Studio-Signature` when `provider_settings.webhook_secret` is configured, normalizes payloads through the profile provider adapter, writes idempotent `EmailEvent` rows through `RecordProviderEventAction`, and updates matching recipient statuses/timestamps for sent/delivered/bounced/complained/opened/clicked/replied/failed events. — `routes/web.php`, `src/Http/Controllers/ProviderWebhookController.php`, `src/Actions/RecordProviderEventAction.php`, `src/Actions/ResolveProviderWebhookProfileAction.php`, `src/Actions/ValidateProviderWebhookSignatureAction.php`, `tests/Feature/ProviderWebhookControllerTest.php`
- **Inbound reply ingestion.** `email_replies`, `EmailReply`, `InboundEmailReplyData`, and `normalizeInboundReply()` exist but are never wired to a route/action. "Replies" in the summary is currently fictional. — table-stakes.
- **Tracking (opens/clicks) endpoints.** `email_tracking_tokens` + `EmailTrackingToken` model + `tracking_token_ttl_days` config exist, but there is no pixel/redirect route, no token minting, and no link rewriting. — differentiator (many CMSes lack first-party open/click tracking).
- **Unsubscribe / suppression self-service + List-Unsubscribe header.** Suppressions can only be created via `SuppressEmailAddressAction` server-side. No public one-click unsubscribe route, no signed unsubscribe token, no `List-Unsubscribe`/`List-Unsubscribe-Post` headers on outbound mail. This is now effectively mandatory for bulk senders (Gmail/Yahoo 2024 rules). — table-stakes.
- **Admin UI (the entire `admin` surface).** No Filament resource/page for templates, variants, profiles, message log, recipient drill-down, or suppression management. Buyers of a "studio" expect to author templates and inspect the send log in-panel. `docs/screenshots.json` confirms zero admin surface. — table-stakes.
- **Done/Shipped: bounce/complaint handling loop.** `RecordProviderEventAction` now calls `SuppressEmailAddressAction` for bounced and complained provider events, creating site-scoped provider-event suppressions for the affected recipient after the event is recorded. — `src/Actions/RecordProviderEventAction.php`, `tests/Feature/ProviderWebhookControllerTest.php`
- **Scheduling / send-at.** `SendEmailData` has no `sendAt`; `SendEmailJob` dispatches immediately. No delayed/scheduled transactional sends. — differentiator.
- **A/B testing of variants.** `email_template_variants` exists and could host A/B, but `ResolveEmailTemplateVariantAction` only picks by site+locale+active, with no split assignment, weighting, or winner tracking. — differentiator.
- **Analytics / reporting.** No aggregate delivery/open/click/bounce metrics surface; `supports` lists `capell-app/insights` but nothing feeds it. — differentiator.
- **Idempotency keys for sends.** No dedupe on `(templateKey, triggeredByType, triggeredById)` — a double-fired listener sends twice. — table-stakes for transactional reliability.
- **Attachments & inline images.** `SendEmailData`/adapters support neither attachments nor embedded images. — table-stakes for many transactional emails (receipts, tickets).
- **Done/Shipped: webhook endpoint verification.** Provider events require a per-profile token whose SHA-256 hash is stored on `email_profiles.webhook_endpoint_token_hash`; profiles can also set `provider_settings.webhook_secret` to require `X-Capell-Email-Studio-Signature` HMAC validation over the raw request body. Provider-specific timestamp tolerance remains future depth for real HTTP adapters such as Postmark API webhooks; `webhook_tolerance_seconds` is still unused. — table-stakes (security).

## 4. Issues / Risks

- **Health checks are declared but non-functional (integrity risk).** `capell.json` advertises 4 checks (3 `critical`) wired to `EmailStudioHealthCheck`, which asserts nothing. A marketplace/host health dashboard would show green for capabilities that don't exist. — `src/Health/EmailStudioHealthCheck.php`, `capell.json`.
- **Manifest still over-declares surfaces vs. reality.** `surfaces: ["admin","frontend","console"]` but admin/frontend ship nothing. The marketplace/composer summary and capabilities now avoid selling replies/events as shipped; the remaining manifest risk is the reserved admin/frontend surface until real routes or resources land. — `capell.json`.
- **Dead schema + Data objects = maintenance debt is shrinking.** `EmailEvent` and `ProviderWebhookEventData` now have a real write path through provider-event ingestion. `EmailReply`, `EmailTrackingToken`, and `InboundEmailReplyData` still await consuming routes/actions. — `src/Models/EmailEvent.php`, `src/Models/EmailReply.php`, `src/Models/EmailTrackingToken.php`.
- **Queue resilience gap (data-loss-ish).** With no `$tries`/`$backoff` on `SendEmailJob` and a catch-all `Throwable` → permanent `Failed` in `DeliverEmailMessageAction`, a brief SMTP blip permanently fails a transactional email (e.g. a password reset) with no retry. — `src/Jobs/SendEmailJob.php`, `src/Actions/DeliverEmailMessageAction.php`.
- **Performance budget risk on multi-recipient sends.** Per-recipient `update()` calls + repeated `recipients()` queries in `DeliverEmailMessageAction` scale linearly with recipients; `capell.json` sets `adminQueryBudget: 40` and `frontendRenderBudgetMs: 20`. A 50-recipient message far exceeds the query budget. — `src/Actions/DeliverEmailMessageAction.php`.
- **PII retention with no enforcement.** Full rendered HTML/text (which may contain names, addresses, reset links, order details) is stored in `email_messages.rendered_html/rendered_text` with a documented 90-day retention that is never applied. GDPR/data-minimisation exposure. — `config/capell-email-studio.php`, `database/migrations/...04_create_email_messages_table.php`.
- **Suppression hashing is unsalted SHA-256.** `EmailAddressNormalizer::hash()` is `hash('sha256', lowercased-email)`. Email address space is enumerable, so a leaked `email_suppressions` table is trivially reversible via rainbow tables. Consider a keyed HMAC (app-key-derived) if these hashes are meant to protect addresses. — `src/Support/EmailAddressNormalizer.php`.
- **No public-output-safety tests because there is no public output yet.** Manifest `cacheSafety.cacheable: false` is correct for now, but the moment tracking/unsubscribe/webhook routes land, they must have anonymous-safety tests (no admin HTML/IDs/selectors leak, signed tokens, no DB-in-Blade). None exist today. The Capell convention explicitly requires these for any public route/rendering change. — (future) `routes/web.php`.
- **Reply test coverage is still thin relative to future claims.** Tests cover send/deliver/suppression/render/resolve/migrations/relationships and provider-event ingestion. `normalizeInboundReply` is still only asserted as a pure transformer because inbound reply ingestion has not shipped. — `tests/Unit/EmailStudioDataAndSupportCoverageTest.php`.
- **i18n half-done.** Enum labels resolve through `__('capell-email-studio::generic.statuses.*')` (good), but there is no per-recipient/per-message language column on the message itself and locale fallback is undocumented. Translations only ship `en`. — `src/Enums/EmailMessageStatus.php`, `resources/lang/en/`.
- **`CHANGELOG.md` is effectively empty.** Only an "Unreleased: Prepared package metadata and documentation" line for a paid, first-party package. — `CHANGELOG.md`.

**Test coverage map (what IS covered):**

- _Unit:_ template registration upsert; variable render (escaping + missing-variable modes, preview vs production); variant resolution (site/locale/fallback); Data/enum/normalizer coverage; SMTP delivery happy-path + provider-id mapping; adapter registry + health metadata; registry persistence pre/post migration; service-provider metadata.
- _Integration:_ deliver (suppression recheck, double-claim guard, stale-claim reclaim); suppression check by hash+scope; send (queued send + cross-site rejection); migrations create tables; model relationships.
- **What ISN'T covered:** webhook event ingestion, inbound reply ingestion, open/click tracking, unsubscribe flow, retry/backoff behaviour, body retention pruning, partial-failure recipient mapping under provider partial-fail, any admin/Filament surface, any public route safety, Postmark-specific behaviour, idempotency/dedupe, attachments.

## 5. Marketplace & Selling

**Critique.** The `capell.json` marketplace `summary` and composer `description` now scope to what ships today: safe template rendering, delivery profiles and adapters, suppression enforcement, queued delivery, and per-recipient send audit. Keep the guard test in place so replies, provider events, webhooks, tracking, and unsubscribe do not reappear in buyer-facing metadata until those ingestion/routes ship.

**Improved 1-sentence summary (honest to current code):**

> Email Studio is Capell's transactional-email engine: site-scoped reusable templates with safe `{{ variable }}` rendering, pluggable delivery profiles and provider adapters, suppression enforcement, and a queued, auditable per-recipient send pipeline.

**Improved 3–4 sentence description:**

> Email Studio gives every Capell site a reliable transactional-email core. Define reusable, locale- and site-scoped templates that render through a deliberately safe placeholder engine (HTML-escaped, missing-variable-strict in production), then send through delivery profiles backed by pluggable provider adapters. Every send is rendered to an immutable snapshot, screened against site and global suppression lists, and delivered via a queue job that records per-recipient outcomes for support and audit. Provider event webhooks can write delivery events back into the audit trail; roadmap slices add open/click tracking, one-click unsubscribe, inbound replies, and an in-panel template studio.

**Screenshot/media gaps.** `capell.json` references 1 screenshot (`extension-card.jpg`) but `docs/screenshots.json` has **0** entries and is blocked because no UI exists. Until an admin surface ships there is nothing to capture beyond the card; the card alone is weak for a "Studio"-branded paid package. Add (post-admin-UI): template editor, variant list, message log with status filters, recipient drill-down, suppression manager.

**Pricing/tier/bundle positioning.** `premium` tier in the `communications` bundle is defensible **only once** the admin surface + event/webhook loop land — today the deliverable is a developer SDK, not an end-user "studio", so a premium price is ahead of the product. Cross-sell is strong and underexploited: it already `supports` `campaign-studio` (bulk/marketing sends can reuse templates, profiles, suppressions), `form-builder` (the docs' canonical example is `forms.confirmation`), and `insights` (feed delivery/open/click metrics). Position Email Studio as the **shared sending substrate** that those three plug into, and bundle accordingly.

**Top differentiators / value props / target buyer.**

- Differentiators: site-scoped (`global` vs `site:N`) templates+suppressions+profiles in one model; immutable rendered snapshot for support reproducibility; provider-agnostic adapter contract; safe-by-default render engine (smaller than Blade, no template injection).
- Target buyer: Capell agencies/operators running multi-site installs who need branded transactional mail (form confirmations, account/order notifications) with auditability and per-site control — without bolting on a third-party ESP SDK per project.

**8–12 keywords/tags:** transactional-email, email-templates, email-suppressions, delivery-profiles, provider-adapters, smtp, postmark, email-audit-log, multi-site-email, queued-email, unsubscribe, bounce-handling.
