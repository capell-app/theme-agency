# Contacts — Improvement & Growth Plan

> Package: capell-app/contacts · Kind: package · Tier: premium · Product group: Capell Content · Bundle: content-product · Status: Draft

## 1. Snapshot

Contacts is an admin-only, schema-owning CRM record layer: five tables (`contacts`, `contact_organisations`, `contact_organisation_memberships`, `contact_leads`, `contact_activities`) backing four models (`Contact`, `Organisation`, `Lead`, `ContactActivity`) and four **read-only** Filament resources plus a dashboard stats widget. Its real value is the ingest pipeline: `SyncContactSourceRecordAction` (`src/Actions/SyncContactSourceRecordAction.php`) calls `FindOrCreateContactAction` to dedupe by hashed email → phone → source identity, then tags, optionally creates a `Lead`, and records a `ContactActivity`. Seven source adapters (`Sync*ContactAction`) wrap that action, wired to first-party events via `Event::listen` in `ContactsServiceProvider` (Form Builder, Access Gate, Events, Comments, Campaign Studio, Shopify `ShopifyCustomerSynced`); Newsletter calls `SyncContactSourceRecordAction` directly from `SyncNewsletterSubscriberContactAction`. PII (`email`, `phone`, names, `source_identifier`, `profile`, lead `context`, activity `payload`) is encrypted at rest with non-reversible HMAC hashes for lookup. Deps: `capell-app/core`, `capell-app/admin`, `lorisleiva/laravel-actions`, `spatie/laravel-data`. Current marketplace summary (verbatim): _"Contacts provides the shared CRM data foundation for contact, organisation, lead, activity, source identity, and first-party package adapter workflows."_ Screenshots: **0** (`marketplace.screenshots: []`) — a mismatch for a premium, first-party-certification-requested tier.

## 2. Improvements (existing functionality)

1. **Admin search on `email`/`display_name` columns silently never matches** — `ContactResource` marks `email` and `display_name` `->searchable()`, but both are `encrypted` casts. Filament search emits `WHERE email LIKE %term%` against ciphertext, which can never hit. Operators will believe the CRM is empty. Either drop `->searchable()` on encrypted columns, or add searchable plaintext helper columns (e.g. search by `email_hash` for exact match, a `display_name` left unencrypted, or a dedicated normalized search column). — `src/Filament/Resources/Contacts/ContactResource.php:29-30` — **M**
2. **Overview stats are not site-scoped** — `BuildContactsOverviewStatsAction` counts `Contact`/`Organisation`/`Lead`/`ContactActivity` across **all** sites with no `site_id` filter, yet contacts are site-scoped and the manifest declares `cacheSafety.variesBy: ["site"]`. On a multi-site install the dashboard widget leaks aggregate counts across tenants and is simply wrong per-site. Scope by the current admin site. — `src/Actions/BuildContactsOverviewStatsAction.php:21-35`, `src/Filament/Widgets/ContactsOverviewStatsWidget.php:34` — **S**
3. **Source-adapter listeners run synchronously on the web request** — every `Event::listen` in `ContactsServiceProvider` binds a plain listener (no `ShouldQueue` anywhere in `src/Listeners`). A Shopify bulk customer sync, form submission, or comment now does find-or-create + encrypt + insert lead + insert activity inline before the response returns. Make the listeners `ShouldQueue` (or dispatch the `Sync*Action` via `::dispatch()`), respecting the manifest's `queueInvalidation: true` intent. — `src/Providers/ContactsServiceProvider.php:127-193`, `src/Listeners/*` — **M**
4. **`SyncShopifyCustomerContactAction` lazy-loads the `connection` relation per event** — `relatedModel()` falls back to `$model->connection()->first()` when the relation isn't eager-loaded (`src/Actions/SyncShopifyCustomerContactAction.php:75-90`). Under a bulk `ShopifyCustomerSynced` storm this is one extra query per customer. Require the emitter to eager-load, or batch. Compounds with improvement #3. — `src/Actions/SyncShopifyCustomerContactAction.php:75-90` — **S**
5. **`fillWhenPresent` never updates existing field values** — once a contact has any non-empty `email`/`name`/etc., later syncs cannot correct it (the guard returns early on any existing string). A customer who fixes their name in Shopify, or a typo'd first capture, is frozen forever. Add an explicit "prefer newer" or "prefer verified source" policy rather than strict first-write-wins. — `src/Actions/FindOrCreateContactAction.php:90-101` — **M**
6. **No index on `last_seen_at` ordering combined with `site_id`** — the contacts table indexes `last_seen_at` alone and `site_id,status`, but the default admin list orders by `last_seen_at` within a site; a composite `(site_id, last_seen_at)` index serves the list page better as volume grows. — `database/migrations/2026_05_31_000001_create_contacts_table.php:34,37-39` — **S**
7. **Stats widget recomputes four `COUNT(*)` on every dashboard load with no cache** — `cacheTags: ["contacts"]` is declared in the manifest but unused; the widget runs the action live. Cache the result keyed by site with `contacts` tag invalidation on contact/lead/activity writes. — `src/Filament/Widgets/ContactsOverviewStatsWidget.php:34`, `src/Actions/BuildContactsOverviewStatsAction.php` — **S**
8. **Adapter actions duplicate the same `stringValue`/`intValue`/`relatedModel` helpers** — the seven `Sync*ContactAction` classes (618 lines total) repeat near-identical scalar-coercion and relation-loading boilerplate. Extract a shared `AbstractSourceContactAdapter` or trait to cut maintenance surface and guarantee consistent null handling. — `src/Actions/Sync*ContactAction.php` — **M**

## 3. Missing Features (gaps)

Mapped against declared `capabilities[]` and CRM norms. **Table-stakes** unless marked differentiator.

- **Contact merge / true deduplication (capability overclaim).** Manifest declares `contacts-deduplication-rules`, but `grep -i merge|dedup` over `src/` returns nothing — the only dedup is first-match identity lookup in `FindOrCreateContactAction`. There is no way to merge two contacts that were created under different identities (e.g. newsletter email vs Shopify GID with a different email), no manual merge UI, no rule configuration. This is the single biggest gap and it is advertised as present. **(differentiator + manifest fix)** — table-stakes for CRM.
- **Operator-facing privacy workflow.** `AnonymizeContactAction` and `BuildContactPrivacyExportAction` exist and are tested, but the only callers are the package's own tests (`grep` across the monorepo confirms no command, Filament action, or other package invokes them). There is no admin button, bulk action, or `contacts:` artisan command to run a GDPR subject access / erasure request. The capability `contacts-privacy-export` / `contacts-privacy-anonymization` is true at the API layer but unreachable for an operator. **(table-stakes)**
- **Editable CRM / write surface.** All four resources are list-only (`getPages()` returns just `index`; policies hard-deny `create`/`update`/`delete`). Operators cannot add a note, change a lead status, assign an organisation, or correct data — Contacts is currently a read-only mirror, not a CRM. At minimum: view pages, manual activity/note creation, lead status transitions. **(table-stakes)**
- **Segmentation & tag management.** Tags live as a free string list inside the encrypted `profile['tags']` (`TagContactAction`), so they are unqueryable (encrypted) and unmanaged — no tag list, no "all contacts tagged X", no segment builder. Move tags to a proper relation or indexed column and add filtering. **(differentiator vs newsletter/campaign-studio cross-sell)**
- **Custom fields.** Arbitrary `profile` JSON exists but there is no schema, no admin-defined custom field registry, no per-field rendering. CRM buyers expect typed custom fields. **(table-stakes)**
- **Import / export.** No CSV/contact import action and no bulk export beyond the per-contact privacy export. Onboarding a customer with an existing list is impossible today. **(table-stakes)**
- **Activity timeline UI.** `ContactActivity` data exists and is recorded, but there is no chronological timeline view on a contact — the activity resource is a flat list. **(table-stakes)**
- **Consent / marketing-state as first-class data.** Shopify `accepts_marketing`/`marketing_state` are buried in `profile`, not modeled as consent records with timestamps and source — needed for GDPR/lawful-basis tracking and for safe Newsletter/Campaign cross-sell. **(differentiator)**
- **Source attribution / first-touch vs last-touch.** `profile['sources']` records `last_seen_at` per source but overwrites; there is no first-touch attribution or per-source history. **(differentiator)**

## 4. Issues / Risks

- **Health check is a stub.** `ContactsHealthCheck` implements `ChecksExtensionHealth` but only returns `compatibleCapellApiVersion()` — it performs **no** check, despite the manifest labeling it _"Contacts models, migrations, and privacy-sensitive storage are discoverable"_ at `severity: critical`. The advertised critical health signal is fake. Implement real assertions (tables exist, models registered, encryption key present, `hash_secret`/`app.key` set). — `src/Health/ContactsHealthCheck.php`, `capell.json:134-142` — **High**
- **Capability `contacts-deduplication-rules` is not implemented** (see §3). The manifest test (`tests/Unit/ManifestRequirementsTest.php:83`) only asserts the _string is listed_, not that a rules engine exists — so the test passes while the feature is absent. Either build merge/rules or drop the capability from the manifest. — `capell.json:117` — **High (truth-in-advertising)**
- **`hash_secret` falls back to `app.key`.** `Contact::hashIdentity` uses `config('capell-contacts.hash_secret') ?: config('app.key')` (`src/Models/Contact.php:215-220`). If `APP_KEY` is ever rotated, every `email_hash`/`phone_hash`/`source_identifier_hash` becomes orphaned and dedup silently starts creating duplicates. No migration/rehash path exists. Document the constraint and provide a rehash command, or require an explicit dedicated secret. — **Medium**
- **PII reachable in plaintext via `profile` payloads in leads/activities.** `Lead.context` and `ContactActivity.payload` are `encrypted:array`, which is good, but `BuildContactPrivacyExportAction` returns fully-decrypted PII as a plain PHP array with no audit-log entry of who exported it. For a GDPR tool, the export itself is a sensitive event and should be logged. — `src/Actions/BuildContactPrivacyExportAction.php` — **Medium**
- **Event-consumer resilience: a throwing adapter breaks the producer.** Because listeners are synchronous (§2.3) and contain no try/catch, an exception inside `SyncContactSourceRecordAction` (e.g. encryption failure, DB constraint) will bubble up and fail the originating form submission / comment / Shopify webhook. Queue + isolate. — `src/Listeners/*` — **High**
- **Cache safety vs declared budget.** Manifest sets `adminQueryBudget: 40` and `cacheable: false, sensitiveOutput: true`. The widget's uncached 4×`COUNT(*)` plus the list page's per-row work are within budget today but unmeasured; there is no test asserting the query count stays under 40. Add a query-count assertion. — `capell.json:122-133` — **Low/Medium**
- **No site scoping in stats = cross-tenant data exposure** (§2.2) — restate as a **High** privacy risk on multi-site installs, not merely a correctness bug.
- **Test gaps:** strong behavioral coverage exists (`ContactFoundationTest.php`, 770 lines, all adapters + dedup-by-email + dedup-by-source-identity + privacy export/anonymize + tags). Missing: (a) the encrypted-column search bug (#2.1) is untested, so it slipped through; (b) site-scoping of stats (the widget test seeds a single site, masking #2.2); (c) listener failure isolation / queueing; (d) no Filament Livewire interaction test (table render/search/sort) — the admin test only asserts class wiring and policy booleans; (e) no architecture test enforcing `Sync*Action` return-type/`AsAction` convention. — `tests/` — **Medium**
- **i18n:** labels are translated (good), but `package.php`/`generic.php` ship `en` only; no other locales. — **Low**
- **No README / CHANGELOG.** Package has `docs/overview.md` only; root `README.md` and `CHANGELOG.md` are absent. For a premium first-party package this hurts marketplace presentation and upgrade communication. — **Medium**

## 5. Marketplace & Selling

**Critique.** The current `summary` and composer `description` are accurate but inward-facing developer prose ("data foundation", "source identity", "package adapter records") — they describe plumbing, not buyer value, and they advertise dedup rules the code doesn't have. With `tier: premium`, `proposedLicense: paid`, `requestedCertification: first-party`, and `privateDocsRequested: true`, shipping **0 screenshots** and no README is a credibility gap; a paid CRM package needs to _show_ the contact list, activity timeline, and dashboard widget.

**Improved 1-sentence summary:**

> The unified CRM layer for Capell — automatically captures contacts, organisations, leads, and activity from your forms, newsletter, events, comments, and Shopify store into one privacy-safe, encrypted record.

**Improved 3–4 sentence description:**

> Contacts gives your Capell site a single, GDPR-aware customer record that fills itself. Every form submission, newsletter signup, event registration, comment, campaign conversion, and Shopify customer is matched to one encrypted contact — deduplicated by email, phone, or source — and enriched with a timeline of leads and activity. Admins get read-through CRM resources and an at-a-glance dashboard, while privacy export and anonymization actions support subject-access and erasure requests out of the box. Built as the shared data spine for the Capell content suite, it powers smarter segmentation across Newsletter, Campaign Studio, and Form Builder. _(Note: tighten "deduplicated" claim to match shipped behavior until merge/rules land — see §3/§4.)_

**Media gaps.** Add at least: (1) contacts list resource, (2) a contact with its activity timeline (once built, §3), (3) the dashboard stats widget, (4) the privacy export/erasure action (once exposed). Minimum 3–4 screenshots before first-party certification.

**Pricing / tier / bundle.** Premium in `content-product` is defensible _only once_ it has a write surface and at least the privacy workflow + merge are reachable; as a read-only mirror it is closer to a free/infra dependency. Position it as the **hub** of the suite: it `supports` access-gate, campaign-studio, comments, events, form-builder, newsletter, shopify-commerce. Cross-sell levers: bundle Contacts as the prerequisite that unlocks segmentation value in **Newsletter** and **Campaign Studio** (both already integrate), surface "contacts captured from this form" in **Form Builder**, and "customers synced" in **Shopify Commerce**. Target buyer: site owners/marketers running multiple capture channels who want one customer view without a third-party CRM.

**Keywords/tags (8–12):** crm, contacts, leads, organisations, customer-data, gdpr, data-privacy, segmentation, shopify-contacts, newsletter-crm, lead-capture, activity-timeline.
